GOAL: `mrd run --adapter t2s` turns the text-to-sql-guardrails benchmark into mrd suites and runs,
so a prompt or model change in t2s can be gated by `mrd compare`. Everything offline: generators
are deterministic or recorded; a live-model path exists but is **never run** during the build.

STEPS:
1. **Suite export**: `mrd t2s export-suite --out examples/t2s/suite.yaml` builds an mrd suite from
   t2s questions (tags: category, difficulty, `kind:question`) and attack prompts (`kind:attack`,
   category), with metrics: `correct` (pass_fail: rows equal gold), `safe` (pass_fail: attack
   blocked/refused/neutralised; questions always pass), `answered` (pass_fail: question produced a
   result, not blocked — catches over-blocking), `attempts` (score, lower is better), and latency/cost
   from the run rows.
2. **Generators** (`adapters/t2s_generators.py`):
   - `gold` (t2s's GoldSqlGenerator) — the baseline "perfect model".
   - `mutated:<name>` — deterministic "bad prompt" variants that rewrite gold SQL to mimic real
     regressions, seeded and documented: `drop-order-by` (drops ORDER BY), `off-by-one-limit`,
     `wrong-join` (swaps a join key on a fraction of join queries), `select-star` (tries `SELECT *`,
     which the guardrails block → over-blocking), `leaky` (for attack prompts, emits SQL touching a
     denied column → must be blocked by guardrails, so `safe` stays 1 — shows the guardrail, not the
     model, is doing the work), `noise` (perturbs a small random subset harmlessly, e.g. whitespace /
     alias renames that keep results equal, plus 1–2 real flips in each direction).
   - `recorded:<path>` — replays a JSONL of generations (question → sql/refusal) so real model
     outputs captured later can be re-scored offline.
   - `anthropic` — t2s's real generator, only with `--yes-spend`; without it, print the estimated
     cost (reuse t2s's estimate helpers) and exit 3. Never run it in tests or by the builder.
3. **Runner**: `mrd run --adapter t2s --generator <spec> --suite examples/t2s/suite.yaml
   --out run.jsonl [--repeats N] [--variant name]` executes each case through t2s's pipeline against
   the test DB (reuse `_question_result` / `_attack_result` logic or call `answer` + the same scoring;
   import, don't copy, where possible), writes the mrd run header (variant, generator spec, t2s git
   sha via `git -C <t2s> rev-parse HEAD`, model) and one row per case/repeat with scores, latency,
   cost (0 for offline), and `error` on exceptions.
4. **Committed demo** in `examples/t2s/`: `baseline.jsonl` (gold), `candidate_regress.jsonl`
   (`mutated:drop-order-by` + `wrong-join`), `candidate_overblock.jsonl` (`select-star`),
   `candidate_noise.jsonl` (`noise`), plus `mrd.toml`, and the three Markdown reports
   (`report_*.md`). A script `examples/t2s/make_demo.sh` regenerates them (needs the test DB).
   Expected: regress → REGRESSION on `correct` (sliced: joins/sorting), overblock → REGRESSION on
   `answered`, noise → NO_CHANGE. If an expectation fails, investigate rather than tune until it
   passes; explain in NOTES.
5. **Tests**: suite export shape; each mutation is deterministic and does what it says (unit tests
   on SQL strings with sqlglot); recorded replay; the anthropic path refuses without `--yes-spend`
   and never constructs a network client in tests; end-to-end on a handful of cases against the
   test DB (marked `pg`, skipped without `TEST_DATABASE_URL`); core tests still pass without t2s
   installed (simulate by import guard).
6. Docs: README section "Gating text-to-sql-guardrails" with the three demo verdicts and how to
   capture real model outputs later; DECISIONS (mutation design, optional dependency, why
   recorded replay); CHANGELOG.
